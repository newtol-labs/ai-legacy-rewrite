# AI 协同重写项目：可复用提示词 + 检查清单

> 来源：卡兹克《开源100万月活级产品AIHOT》的 12 步重写流程与架构对比图，已整理成通用模板。
> 用法：`{{...}}` 是占位符，按项目替换。模型角色按下面三类分配，不绑定具体模型：
> - **主力开发（Dev）**：负责重写和修复，用最强的长任务模型。
> - **审查 A / 审查 B（Rev-A / Rev-B）**：和 Dev 不同家的模型，负责并行交叉审查。
> - **子 Agent（Sub）**：按功能模块拆出，每次都从干净的上下文开始。

---

## 0. 启动前：要不要重写？

### 提示词 P0：评估重写必要性
```text
请只读分析当前仓库 {{repo_path}}，判断应该“继续局部修复”还是“另起目录整体重写”。
要求：
1. 用可核实的数字说话：主链路文件数和行数、超大文件（>1000 行）清单、数据模型/表数量、
   触发器/存储过程数量、配置开关数量、跨层耦合点（例如缓存要在应用、Nginx、CDN 多层协调）。
2. 列出“改 A 坏 B”的典型耦合链路，至少 3 条，并附文件路径。
3. 明确指出：换成空目录也清不掉的东西（含糊需求、互相冲突的规则、历史例外），逐条列出。
4. 给出结论和理由；如果建议重写，说明前提条件（例如有可运行的线上版本可作为验收基准）。
不要修改任何文件。
```

### 检查清单 C0：重写前提
- [ ] 有**可运行的线上/旧版本**，能当端到端验收基准
- [ ] 数据可以完整导出，能在新系统里彩排
- [ ] 能列出所有**对外契约**（页面 URL、API、RSS、SDK、Webhook 等）
- [ ] 项目规模在可控范围内（超大系统应先按模块渐进替换，不要一次性全部重写）
- [ ] 已经清楚哪些问题是“需求本身的混乱”，不是“代码烂”

---

## 1. 提炼：把旧代码变成功能契约（两个模型并行）

### 提示词 P1：生成功能文档 + 交接包（Dev 和 Rev-A 各跑一份）
```text
目标：把 {{repo_path}} 提炼成一份“与实现无关”的完整功能规格和交接包，
供一个新团队在【完全不看旧代码】的前提下，在新目录 {{new_dir}} 从零重写。

功能文档必须包含：
1. 产品能力清单：每项能力写输入、输出、触发方式、边界条件、失败行为。
2. 对外契约：所有 URL、API（请求/响应示例）、RSS/Feed、MCP/SDK、缓存头、跳转规则。
   逐条编号，后续用来做兼容探针。
3. 数据：核心实体、字段含义、状态机、数据归属（哪个模块写、哪些模块读）。
4. 业务规则与“踩坑细节”：历史 bug、隐性约定、时区/排序/去重/幂等等容易漏的点。
   每条标注来源文件路径。
5. 需要废弃或重新定义的规则：互相冲突的、含糊的、只为兼容历史而存在的。
6. 验收场景：Given/When/Then 格式，覆盖全部能力。

架构约束：
- 架构分离，按“多 Agent 并行开发”来设计：明确模块边界、模块间契约、任务依赖图。
- 前后端分离；各服务独立构建、独立部署。
- 模型/外部服务都做成可替换的能力。

交接包必须包含：环境与部署说明、依赖服务清单、种子数据/人工金标样本、
信源或配置清单、运行和验收命令。
密钥只写“名称 + 获取方式”，不要把明文写进文档或仓库。

请先输出目录结构和能力清单让我确认，再展开全文。
```

### 提示词 P2：交叉对照补全（Rev-B）
```text
你会收到两份独立生成的功能文档/交接包（{{doc_a}}、{{doc_b}}）和旧仓库 {{repo_path}}。
请：
1. 合并两份文档，逐项标注：仅 A 有 / 仅 B 有 / 两者冲突。
2. 对照旧代码，找出两份都漏掉的功能、分支逻辑、配置和边界处理（附文件路径和行号）。
3. 标出不合理的设计（对重写有害的历史包袱），并给出替代规则。
4. 输出一份最终版规格：{{final_spec}}，另附“变更与补漏清单”。
```

### 检查清单 C1：规格质量
- [ ] 每项能力都有验收场景，每个对外契约都有编号
- [ ] 数据归属清楚：同一份数据只有一个写入方
- [ ] 踩坑细节都能追溯到旧代码的具体位置
- [ ] 冲突和含糊的规则已经**做了决定**，不是原样搬过来
- [ ] 任务依赖图可以直接拆成并行任务
- [ ] 交接包里**没有明文密钥**，或者已经放进 `.gitignore`，确认不会进仓库

## 2. 重写：不看旧代码（Dev）

### 提示词 P3：从零重写
```text
在空目录 {{new_dir}} 中实现系统。
唯一依据：{{final_spec}}、交接包、线上站点 {{prod_url}} 的实际行为（可以做端到端观察）。
严禁读取 {{repo_path}} 下的任何旧代码。

架构原则：
- 进程边界：{{services，例如 web / api / worker}} 独立；前端只通过 HTTP 取数据，
  前端进程不持有数据库地址和密钥。
- 业务规则放在应用代码里，不使用数据库触发器和存储过程。
- 一张表只管一件事；读模型必须能从源表重建。
- 迁移只用纯 SQL，只做向后兼容的增量变更。
- 业务写入和后续异步任务放在同一个事务里入队。
- 所有对外出口共用一个公开读取层，HTTP/缓存策略只定义一次。
- 不做双写、不做影子写、不留新旧开关；只保留外部依赖的安全阀。
- 模型调用：结构化输出 + schema 校验；读取路径永远不调用模型。
- 前端组件化，统一控件。

执行方式：按依赖图逐个任务推进；每完成一个模块，就跑一遍对应的验收场景并记录结果。
遇到规格没写清楚的地方，记到 {{open_questions}}，不要自行编造需求。
```

### 检查清单 C2：每个 PR 的门禁（全部自动化）
- [ ] 类型检查
- [ ] 构建（前端和各服务）
- [ ] **空库迁移**（从零跑完所有迁移）
- [ ] 启动 api 和 web 冒烟测试
- [ ] 对外兼容探针（对照契约编号）
- [ ] 不变量测试（例如去重、排序、幂等、计数守恒）

---

## 3. 审计：新旧逐项比对（Rev-A 和 Rev-B 并行）

### 提示词 P4：用户体验层面的一致性审计
```text
对比新项目 {{new_dir}} 和旧项目 {{repo_path}}（及线上 {{prod_url}}）。
只关注功能和行为，不评价代码风格。
逐项检查：每项能力、每个对外契约、每条业务规则、每个验收场景，
判断新系统在用户体验层面能否完美还原。
输出审计报告，每条包含：编号、问题描述、证据（旧实现位置 / 新实现位置 / 复现步骤）、
严重级别（阻断 / 重要 / 次要）、修复建议。
没有证据的疑点单独列在“待证实”里，不要混进结论。
```

### 提示词 P5：清空上下文后，按模块用子 Agent 复核（Dev 调度）
```text
（在新会话中执行，不继承之前的开发上下文）
把系统按功能模块拆成 N 个子任务：{{module_list}}。
每个子 Agent 只负责一个模块：阅读该模块的规格条目、新代码对应目录、旧代码对应目录，
只比对“功能和逻辑细节”，忽略实现差异。
输出：遗漏的功能 / 不一致的逻辑 / 规格里没写但旧代码里有的行为，都附证据。
最后汇总去重，生成修复清单。
```

### 提示词 P6：Bug 与安全审查（Rev-A 和 Rev-B 并行）
```text
审查 {{new_dir}}，找出潜在的 bug 和安全漏洞：
鉴权/越权、注入、密钥泄露、SSRF、并发/竞态、事务边界、重试与幂等、
缓存一致性、时区、分页与排序、错误处理、资源泄漏。
每条都要给出触发条件和证据，按严重级别排序。
```

### 检查清单 C3：审计闭环
- [ ] 两份审计报告的问题都已经修复，或者明确标记为“不修”并写明理由
- [ ] 子 Agent 复核是在**干净的上下文**里执行的
- [ ] 所有“阻断 / 重要”问题修复后都做了回归
- [ ] “待证实”的疑点，要么已证实，要么已关闭（UNKNOWN 不等于 PASS）

## 4. 彩排与切换

### 提示词 P7：影子彩排
```text
导出旧系统的全部生产数据，在 {{staging_server}} 上导入新系统并完整运行。
让新旧系统并行跑 {{hours，例如 6}} 小时，持续比对：
- 对外兼容探针（全部契约编号）
- 关键产出的数量和内容（例如日报/周报条数、主题页数量、Feed GUID）
- 延迟 p50/p95、错误率、队列积压
发现差异就定位并修复，然后重跑比对，直到全部一致。输出彩排报告。
```

### 检查清单 C4：上线切换
- [ ] 至少完成 1 次（最好 2 次）完整的生产数据彩排
- [ ] 兼容探针 **N / N 全部通过**，关键产出数量一致
- [ ] 全面端到端测试通过
- [ ] 回滚方案已经演练过（旧系统保持可切回）
- [ ] 旧接口有过渡期，并写明下线日期
- [ ] 切换窗口和影响范围已经确认（例如只暂停内容更新、站点不停）
- [ ] 切换前后各记录一份性能基线

---

## 5. 上线后

### 提示词 P8：基于真实数据的性能优化
```text
基于上线后 {{days}} 天的真实访问日志和监控数据，
分析并优化：缓存命中率、CDN 策略、页面体积、慢查询、慢接口。
每项优化都要给出改前/改后数据，口径保持一致（同一时间段、同一台服务器、同一个 CDN）。
```

### 检查清单 C5：持续运营
- [ ] 告警分级，重复告警要合并
- [ ] 用前后对比指标衡量成效：代码行数、依赖数、延迟、错误数
- [ ] 每个数字都注明统计口径
- [ ] 新需求要**先更新规格文档**，再改代码，防止再次长成屎山

---

## 附：最容易踩的 5 个坑
1. **让重写模型读了旧代码**：会被原来的写法带偏，重构做不彻底。
2. **把混乱的需求原样搬过去**：新目录也会长成新的屎山。
3. **写和审用同一个模型、同一段上下文**：盲区会重复出现。
4. **没有影子彩排就直接切换**：生产数据里的边界情况在测试环境跑不出来。
5. **交接包里的明文密钥进了仓库或被外传**。
