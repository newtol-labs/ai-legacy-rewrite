# 候选架构原则（按项目取舍，不是默认约束）

来源：AIHOT 2.0 新旧对比（内容型网站：采集 → 模型精选 → 聚合 → 网站/API/RSS/MCP 输出）。
使用方式：在 P1 后、P3 前逐条判断"采用 / 调整 / 不采用"并写理由，只把采用的条目贴进 P3。
判断依据是本项目的部署约束、性能要求、数据形态、团队/Agent 维护方式，不是"原案例这么做"。

| # | 原则 | 为什么 | 何时不适用 / 如何调整 |
|---|---|---|---|
| A1 | 逻辑模块边界清晰，模块间只通过契约交互；前端不持有数据库地址和凭据 | 便于 Agent 用最少上下文定位修改；安全 | 通用。**注意**：模块化 ≠ 必须拆成独立服务，单体内模块化同样满足 |
| A1b | web / api / worker 拆为独立进程、独立部署 | 故障隔离、独立扩缩 | 小工具、单机脚本、低流量系统不需要；拆分带来的运维成本要论证 |
| A2 | 业务规则放在应用代码里，不放数据库触发器和存储过程 | 规则可见、可测试、可审查 | 数据库内强一致约束（唯一键、外键、check）仍应保留；已有大量存储过程且团队熟悉时评估迁移代价 |
| A3 | 一张表只管一件事；读模型能从源表重建 | 避免同步链路，便于修数据 | 基本通用 |
| A4 | 迁移只做向后兼容的增量变更；查询层轻量 | 迁移可控、可回滚 | ORM 可保留，关键是守住增量迁移；不兼容变更要走 P7c 的迁移策略 |
| A5 | 业务写入和后续异步任务在同一事务内入队（outbox / pg-boss 等） | 不会"写成功了任务却丢了" | 有异步流程时适用 |
| A6 | 对外出口共用一个公开读取层，HTTP/缓存策略只定义一次 | 避免应用、Nginx、CDN 各写一份 | 对外输出较多时适用 |
| A7 | 不做双写、不留新旧开关，只保留外部依赖的安全阀 | 消除新旧并存复杂度 | **渐进替换或增量追平期间需要短期双写**，写明移除日期即可 |
| A8 | 模型调用数量少、结构化输出 + schema 校验；读取路径不调用模型 | 成本和延迟可控 | 实时推理类产品要改写 |
| A9 | 模型/外部服务做成可替换能力 | 更强模型可直接替换 | 通用 |
| A10 | 契约驱动：先定模块和数据归属，再拆带依赖的并行任务 | 多 Agent 并行互不踩踏 | 通用 |
| A11 | 前端组件化，统一控件 | 一致性；Agent 定位修改需要更少上下文 | 有 UI 时适用 |
| A12 | 单一主语言，减少依赖和脚本 | 降低认知负担 | 有强理由（CAD/数值计算需 Python 等）时可多语言，划清边界即可 |
