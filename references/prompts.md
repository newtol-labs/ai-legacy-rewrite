# 提示词模板（P0–P8）

占位符：`{{repo_path}}` 旧仓库，`{{new_dir}}` 新目录，`{{prod_url}}` 线上/基准地址，`{{final_spec}}` 最终规格，`{{mode}}` 重构/重写。

## 目录
- P0 评估改造方式（阶段 0）
- P1 功能规格 + 交接包 + 已批准差异（阶段 1，Dev 与 Rev-A 各跑一份）
- P2 交叉对照补全（阶段 1，Rev-B）
- P3 隔离重写（阶段 2，Dev，新会话，工作目录不含旧仓库）
- P4 一致性审计（阶段 3，Rev-A 与 Rev-B 并行）
- P5 清空上下文后按模块复核（阶段 3，Dev 调度 Sub）
- P6 Bug 与安全审查（阶段 3）
- P7 副作用清单 → 影子彩排 → 迁移与回退（阶段 4）
- P8 按真实数据优化（阶段 5）

---

## P0 评估改造方式
```text
只读分析仓库 {{repo_path}}，判断哪种改造方式最小足够：局部修复 / 行为不变的重构 / 按模块渐进替换 / 整体重写。
1. 用可核实的数字描述现状：主链路文件数与行数、超大文件清单、数据模型数量、触发器/存储过程数量、
   配置开关数量、跨层耦合点。只报告有证据的项，不凑数。
2. 列出确实存在的"改 A 坏 B"耦合链路，附文件路径；有几条写几条。
3. 指出换目录也清不掉的东西：含糊需求、互相冲突的规则、历史例外，逐条列出。
4. 对每种改造方式估算：预期收益、迁移代价、主要风险、前提条件（例如是否有可运行基准、数据能否停写）。
5. 给出推荐及理由。推荐"局部修复"或"不改"也是合法结论。
不要修改任何文件。
```

## P1 功能规格 + 交接包 + 已批准差异
```text
目标：把 {{repo_path}} 提炼成与实现无关的功能规格和交接包，供一个新团队在完全不接触旧代码的前提下，
在 {{new_dir}} 从零实现。本次改造类型：{{mode}}。

功能规格必须包含：
1. 产品能力清单：每项写输入、输出、触发方式、边界条件、失败行为。
   能力清单要与至少两个独立来源交叉核对（路由/入口表、后台任务表、对外消费者、历史回归用例等，按项目实际选），
   标明每项能力的来源证据。
2. 对外契约：全部 URL、API（请求/响应示例）、Feed、SDK、Webhook、缓存头、跳转规则，逐条编号（C-001…）。
3. 数据：核心实体、字段含义、状态机、数据归属（谁写、谁读）。
4. 业务规则与踩坑细节：历史 bug、隐性约定、时区/排序/去重/幂等；每条标注来源文件路径。
5. 已批准差异清单（草稿）：建议废弃或重定义的规则，每条写"现状行为 / 建议目标行为 / 理由 / 影响"，
   状态先标"待批准"。改造类型为重构时，此清单应为空或只含纯技术项。
6. 验收场景：Given/When/Then，覆盖全部能力；标明每个场景对应的比较规则
   （精确一致 / 归一化后一致 / 容差范围 / 业务不变量）。

架构要求（只定逻辑边界，不定部署形态）：
- 明确模块边界、模块间契约、数据归属；输出任务依赖图（任务编号 + 前置依赖），便于并行开发。
- 外部服务和模型做成可替换能力。
- 部署形态（单体 / 多服务）、存储、队列等由阶段 2 前按 architecture-principles.md 取舍决定，这里不预设。

交接包必须包含：环境与部署说明、依赖服务清单、种子数据/人工金标样本、配置清单、运行和验收命令。
凭据只写名称、用途、获取方式，任何情况下不得写入明文。

先输出目录结构和能力清单让我确认，再展开全文。
```

## P2 交叉对照补全
```text
你会收到两份独立生成的规格/交接包（{{doc_a}}、{{doc_b}}）和旧仓库 {{repo_path}}。
1. 合并两份文档，逐项标注：仅 A 有 / 仅 B 有 / 两者冲突。
2. 对照旧代码和 P1 要求的独立来源，找出两份都漏掉的能力、分支、配置和边界处理，附路径和行号。
3. 审阅已批准差异清单草稿：补漏、去重、标出会改变业务含义需要用户决定的项。
4. 输出最终规格 {{final_spec}} 和"变更与补漏清单"。
```

## P3 隔离重写
> 启动前由人工保证隔离：新开会话；工作根目录设为 `{{new_dir}}`；旧仓库不挂载、不软链、不在任何可访问路径；
> 会话输入只有最终规格、交接包、经取舍的架构原则和线上地址。隔离靠环境实现，不靠模型自觉。

```text
本会话的工作根目录是 {{new_dir}}，在其中从零实现系统。
唯一依据：{{final_spec}}、交接包、线上站点 {{prod_url}} 的实际行为（可端到端观察）。
旧代码不在你的可访问范围内，不要尝试寻找或推测它的实现。

架构原则（已按本项目取舍）：
{{粘贴取舍后的 architecture-principles 条目}}

执行方式：
- 按任务依赖图推进；每完成一个模块，跑对应验收场景并记录 PASS / FAIL / 未执行。
- 每个 PR 通过门禁：{{按项目取舍后的门禁列表，例如 类型检查 → 构建 → 空库迁移 → 启动冒烟 → 兼容探针 → 不变量测试}}。
- 规格没写清的地方记到 {{open_questions}}（问题 + 影响模块 + 临时假设），由 Spec Owner 查证后补规格；
  得到答复前按临时假设继续，代码中标注 TODO(spec)。
- 不自行编造规格里没有的需求；不自行决定业务含义。
```

## P4 一致性审计
```text
对比新项目 {{new_dir}} 与旧项目 {{repo_path}}（及线上 {{prod_url}}）。只关注功能和行为，不评价代码风格。
验收标准：{{final_spec}} 中的目标契约 + 已批准差异清单。
- 新旧不一致且差异在已批准清单内 → 记为"预期变化"，不是缺陷。
- 新旧不一致且不在清单内 → 缺陷，或提请 Spec Owner 决定是否批准。
- 旧有、规格没写、新没有 → 疑似遗漏，附旧实现位置。
逐项检查每项能力、每个契约编号、每条业务规则、每个验收场景，按规格中的比较规则判断。
输出报告，每条含：编号、类型（缺陷/预期变化/疑似遗漏）、证据（旧位置/新位置/复现步骤）、
严重级别（阻断/重要/次要）、修复建议。无证据的疑点单独列"待证实"。
```

## P5 清空上下文后按模块复核
```text
（新会话执行，不继承开发上下文）
把系统按功能模块拆成子任务：{{module_list}}。每个子 Agent 只负责一个模块：
读该模块的规格条目、已批准差异、新代码对应目录、旧代码对应目录，只比功能和逻辑细节，忽略实现差异。
输出：遗漏的功能 / 不在批准清单内的不一致 / 规格没写但旧代码有的行为，都附证据。
汇总去重生成修复清单。若本轮没有新问题或问题与 P4 重复，明确写"无新增"，不再扩展范围。
```

## P6 Bug 与安全审查
```text
审查 {{new_dir}}：鉴权/越权、注入、密钥泄露、SSRF、并发/竞态、事务边界、重试与幂等、缓存一致性、
时区、分页与排序、错误处理、资源泄漏。每条给出触发条件和证据，按严重级别排序。
```

## P7 副作用清单 → 影子彩排 → 迁移与回退

### P7a 副作用清单（彩排前必做）
```text
列出新旧系统运行时所有对外副作用：发通知/邮件/IM、Webhook、支付、付费 API 或模型调用、写第三方系统、
外发队列消息、定时任务。对每项写：触发条件、彩排时的隔离方式（指向桩/沙箱/禁用/只读凭据）。
再列出彩排需要读取的数据范围，能用脱敏快照或授权样本就不用全量生产数据。
没有任何对外副作用时明确写"无"，并说明依据。
```

### P7b 影子彩排
```text
按 P7a 的隔离方式，在 {{staging_env}} 用 {{数据范围}} 运行新系统 {{hours}} 小时，与旧系统输出并行比对：
- 兼容探针（全部契约编号），按规格里的比较规则判断
- 关键产出的数量与内容
- 延迟 p50/p95、错误率、队列积压
记录被测代码版本、规格版本、数据快照版本。差异分类：缺陷 / 预期变化 / 允许的非确定性。
缺陷修复后重跑；预期变化和允许的非确定性不需要"修到一致"。
输出彩排报告：探针 PASS/FAIL/未执行/不适用各多少、差异清单及处置、性能基线。
```

### P7c 迁移策略与回退（切换模式下必做）
```text
基于 {{final_spec}} 和实际数据，给出切换方案：
1. 切换策略选一种并说明理由：停写窗口一次性迁移 / 增量追平（双跑期新写入如何同步）/ 只读过渡期。
2. 数据迁移：一致性点、转换规则、关联完整性校验、队列去重、切换后校验方法。
3. 回退方案：切换后新系统产生的数据如何保留或回灌旧系统；旧代码能否读新数据；
   无法无损回退时明确说明，并给出前向修复方案。
4. 演练：在彩排环境实际执行一次迁移 + 一次回退，记录结果。
5. 旧接口过渡期及下线日期。
切换本身需要用户明确确认，不在本提示词内执行。
```

## P8 按真实数据优化
```text
基于上线后 {{days}} 天的真实访问日志和监控，分析并优化缓存命中率、CDN 策略、页面体积、慢查询、慢接口。
每项给出改前/改后数据，口径一致（同时间段、同环境）。
```
