## 初版结论（2026-09-29 第一轮，保留作对照）

**存在实质问题。当前版本更接近“从单个案例改写的工作流提示词集”，不宜直接作为无人值守的重写与上线操作规程。**

值得保留的是功能契约、模块边界、验收证据和渐进加载。需要修正的是：把重写当成默认路径、把架构偏好当成通用约束、把多轮审查当成正确性保证，以及没有定义充分的数据迁移和安全隔离条件。

本次只审阅，未修改 Skill、未导出生产数据、未运行项目或执行上线。以下“反例”是对规则的逻辑压力测试，不是已经发生的事故，也不是模型实测结果。

## 第一性原理：这个 Skill 究竟应该优化什么？

软件改造的目标不是“新代码更少、模型更多、架构更新”，而是：

> 在用户授权的范围和成本内，保留必须保留的行为与数据，完成明确需要的改变，并提供与风险相称、可以复现的证据。

据此审查以下条件：

- **目标正确**：允许结论为不改、局部修复、渐进替换或整体重写，而不是预设重写。
- **行为正确**：分清现状、期望和已批准差异，不能机械复刻旧缺陷。
- **数据与外部影响可控**：彩排不应成为第二个生产执行者；代码回退不等于数据恢复。
- **证据有效**：通过已生成的测试，不等于覆盖了全部应测试的行为。
- **过程可执行且有界**：读取隔离、退出条件、失败状态和预算应明确，不能依赖口头自证。

## R01｜高：密钥规则自相矛盾，`.gitignore` 被当成了安全边界

**证据**
- P:53 要求不要把明文密钥写进文档或仓库。
- S:53 却允许“如果确需打包明文，必须放进 `.gitignore`”。
- C:19 允许“没有明文密钥，或者已经放进 `.gitignore`”通过清单。

**反例**：交接包含生产凭据，已被忽略提交，但仍被打成压缩包交给下一个 Agent。按清单可以通过，凭据却已越过原有边界。

**判断**：规则只检查版本控制排除，没有约束压缩、日志、上下文传递和文件上传；“不提交”不能替代“不得泄露”。这是明确的内部冲突，不是泛泛的安全担忧。

**最小修正方向**：交接包只记录密钥名称、用途与受控获取方式；取消明文例外。需要运行时由获授权的环境注入最小权限凭据，不能靠 `.gitignore` 放行。

## R02｜高：影子彩排没有外部副作用隔离

**证据**
- P:114–119 要求导出全部生产数据、导入新系统“完整运行”、新旧并行并修复差异。
- S:54 对切换、删除、改写历史要求确认，却没有规定彩排的数据读取、凭据、网络出口与写入范围。

**反例**：复制了任务记录和生产配置，新 worker 同旧 worker 一起触发通知、Webhook 或付费任务。两个实例都正确运行，业务却被执行了两次。

**判断**：旁路验证的关键不是“再跑一套”，而是“运行候选实现但不重复真实业务副作用”。当前 P7 没有这个前提。

**最小修正方向**：先声明允许读取的数据范围和允许发生的副作用；优先使用脱敏快照或已授权样本，隔离数据库、队列与凭据；通知、支付等出口指向桩服务或沙箱。真实外部调用和数据导出另按既有授权核对，不擅自扩大。

## R03｜高：迁移与回滚只写了动作，没有说明如何保持数据正确

**证据**
- P:114 直接从导出旧数据跳到导入新系统。
- C:24 只检查空库迁移，C:41 要求回滚演练且“旧系统保持可切回”。
- A:11 将纯 SQL、向后兼容增量迁移与“可回滚”联系起来。

**反例**：快照导出后旧系统继续接单；新系统上线又产生了新字段和新订单。此时切回旧代码，快照之后的写入怎样补齐？旧代码能否读新数据？现有规则没有答案。

**判断**：空库可启动不能证明旧数据可升级；保留旧程序也不能证明切换后数据可恢复。这两者必须分别验证。

**最小修正方向**：针对实际系统选择停写窗口、增量追平或其他迁移机制，明确一致性点、转换规则、关联完整性、队列去重、最终追平和校验方法。回退方案应说明切换后的新写入如何保留；无法无损回退时，应明确限制并准备前向修复方案。不能把某一种技术路线强制用于所有项目。

## R04｜高：旧行为和目标行为没有优先级，改对的东西可能被审计改回去

**证据**
- P:43、64 要求废弃或重新定义不合理规则。
- P:71 同时将最终规格和线上实际行为作为依据。
- P:87–88 要求新系统在用户体验层面“完美还原”。

**反例**：最终规格已经批准修正旧的金额舍入规则；审计发现新旧结果不一致，按“完美还原”标准又将修正判为缺陷。

**判断**：当前规则无法区分“意外回归”和“批准后的变化”。也没有说明 AI 可以决定哪些技术细节、哪些业务行为必须由用户或业务负责人决定。

**最小修正方向**：分别记录现状行为、目标契约、已批准差异。验收以目标契约为准，旧行为用于发现漏项；改变业务含义的差异需要明确授权，不能由审查者为了消除差异自动改回去。

## R05｜高：验收门槛可以被自证或关闭问题绕过

**证据**
- P:37–44 从旧库生成能力、契约及验收场景；C:39 将“探针 N/N 全通过”作为切换条件。
- C:31 允许问题标记为“不修”并写理由；C:34 允许疑点“已关闭”，没有定义关闭所需证据。
- T:18–28 没有记录被测版本、测试运行标识、比较规则或独立的通过/未运行状态。

**反例 A**：同一轮提炼漏掉退款能力，测试清单也没有退款项，剩余探针全部通过。数字是真实的，完整性结论却不成立。

**反例 B**：重要问题没解决，仅填入“不修：风险可接受”便被视为处理完成，谁有权接受风险没有规定。

**反例 C**：模型输出或时间字段存在合理变化，P:119 要求“直到全部一致”，导致不断修复本来允许的差异。

**最小修正方向**：
- 将能力清单与路由、任务、消费者、历史回归用例等不同来源交叉核对；来源按项目实际选，不强行穷举。
- 固定本次候选的代码、规格、数据版本与必测项；明确精确比较、归一化比较、容差或业务不变量。
- 分开记录 PASS、FAIL、未执行/证据不足、不适用；风险接受不是测试通过。
- 无证据的猜测不登记为已确认缺陷；关键测试未执行则如实阻断相应放行，不能为清空清单而关单。
- 重要问题的豁免需说明责任人、理由和影响，不能由执行 Agent 自行改判。

## R06｜低（已修订）：“不读旧代码”方法成立，原版缺的是隔离机制

> 2026-09-29 修订：初版把本条定为“中”，并质疑“读旧代码会被带偏”是未经证明的假设、建议改为“允许理解事实”。经用户指正后收回：在重写场景下，模型对上下文内代码的锚定是有充分依据的，原作者的一手经验也证实了这一点；在原仓库里开新会话同样不够，一次 grep 就会把旧实现读进上下文。“允许理解旧实现”会把方法本身拆掉。本条重新定性为**机制没写清**，而非**方法有问题**。

**初版证据（问题所在）**
- 原 P:7 安排 Dev 参与提炼，P:9 让 Dev 重写，P:72 只写“严禁读取旧代码”，误导成同一实例既读又“不读”。
- 原 C:28 要求“确认重写过程中没有读取旧代码”，是无法核实的自证打勾。

**成立的部分**：禁令靠模型自觉，没有物理隔离；同一会话“停止读取”不等于清除已读上下文。

**不成立的部分**：把“不读旧代码”降为可选策略、允许重写者理解旧实现。

**已落实的修正**（当前 Skill 版本）
- SKILL.md 核心理念 1 改为“重写阶段与旧代码物理隔离”，硬要求：新目录 + 新会话 + 旧仓库不在可访问路径。
- 角色说明改为按会话区分，同一模型可兼任提炼与重写，但重写必须在未接触旧代码的新会话里；新增 Spec Owner 角色负责回答 open_questions，需要时由他查旧代码补规格。
- P3 增加人工隔离前置说明，并把 open_questions 回流机制写入（临时假设 + TODO(spec) 标注），重写者不自行寻找或推测旧实现。
- C2 把“确认没读过”替换为可核实项：新会话、工作根目录不含旧仓库（记录路径）、疑问全部经 open_questions 回流。
- 审计阶段（P4/P5）读旧代码是必要的，保持不变。

**剩余风险**：隔离仍依赖人工按前置说明搭环境；Skill 无法自行验证工作目录内是否真的没有旧代码，只能要求记录路径。

## R07｜中：名义上架构可调整，实际在更早的模板里已经写死

**证据**
- S:41、51 说 P3 前按业务调整架构。
- P:46–49 在 P1 阶段就要求前后端分离、各服务独立构建部署，并围绕多 Agent 并行设计。
- A:9 将不用触发器和存储过程标为“基本通用”；A:11、14、15 预设 SQL 迁移、新旧逻辑及读取路径策略。
- C:22–28 将类型检查、构建、空库迁移等设为统一必过门槛。

**反例**：一个本地数据处理工具没有前后端和数据库；为了满足模板，反而引入不需要的服务和迁移步骤。

**判断**：参考文件的“可以调整”不能自动消除主流程的硬性要求。模块边界是逻辑设计，独立部署是运行方式，两者不应绑定；为 Agent 容易并行而改变生产架构，也缺少成本论证。

**最小修正方向**：先确认部署、性能、数据与团队约束，再选架构；将原案例做法降为候选方案。检查清单允许有理由的不适用，但不得用“不适用”隐藏缺证据。

## R08｜中：缺少明确的任务模式和正常退出分支

**证据**
- S:4–8 同时覆盖评估、方案、规格和重写。
- S:29–37 给出单向全流程；S:47 和 C:3 要求未通过不要跳阶段。
- P:20 允许建议继续局部修复，但后续没有对应执行分支。
- P:55 固定要求先确认目录和清单；C:6–7 把可运行基准、可导出数据设为统一前提。

**反例**：用户只要重构方案，执行器却把“未进入重写”视为未完成；或仅需整理规格，却因没有线上基准而停住。

**判断**：上层授权规则仍能限制越界，不能断言 Skill 一定会擅自执行；但 Skill 自身没有可靠表达“用户要什么、做到哪里停止”。

**最小修正方向**：入口明确评估、方案、提炼、实施、审阅、切换等模式，只加载所需阶段。评估结论为不重写是成功退出；已有明确授权的低影响工作不重复加审批，涉及业务目标或外部影响的变化才补确认。

## R09｜中：流程偏向形式上的投入，缺少成本和停止条件

**证据**
- P:22–24 强调文件/表/开关数量，并强制至少三条耦合链路。
- S:25、33–35 固定多角色、多份规格、多轮审查；P:97 使用未限制规模的 N 个子任务。
- P:119 要求修到全部一致，没有时间、轮次或证据增益的停止条件。

**反例**：实际只有一条可证实耦合链路，提示词却要求至少三条；不同审查者反复报告相同问题，流程仍必须继续。

**判断**：文件大、代码多是线索，不是重写收益。多模型只是潜在的视角补充，不能自动生成独立证据；当前也没有保证能选择不同模型的机制。

**最小修正方向**：只报告确有证据的问题，不凑数；比较修复、替换和重写的预期收益及迁移代价。审查按风险与独立工作价值启用，不默认每次跑满；设置有界迭代，无新证据、重复失败或缺授权时停止并报告。角色不同不冒充独立模型或独立验证。

## R10｜中：缺少行为评测，读取成功不能证明 Skill 可靠

**证据**
- 本次目录清单仅显示 SKILL.md、references/ 和 assets/，没有顶层 evals/。
- 上一轮创建记录只验证了 Skill 可读取，并明确说尚未用真实请求测试。

**判断**：不能据此断言 Skill 实际触发错误，也不能声称它已证明节省 Token、提高正确率或稳定执行。这些性质尚无行为测试证据。

**最小修正方向**：先补少量高价值的反例评测，再考虑更广泛使用；无需一开始建立庞大的评测平台。无评测不是所有 Skill 都不能使用的理由，但本 Skill 涉及生产数据和切换，不能只靠加载成功就放行这些能力。

## 建议优先级

1. **先堵高风险缺口**：密钥明文例外、彩排外部副作用、迁移后写入与回退、业务差异和验收放行。
2. **再去掉不必要的硬约束**：架构改为条件化决策，多角色改为按需使用。（初版此处还写了“隔离式重写改为可选策略”，已撤回，见 R06 修订。隔离式重写是该方法的核心，应保留为硬要求，只是把保证方式从“禁令”改为“环境隔离”，已完成。）
3. **最后验证可用性**：收敛入口和退出条件，做边界用例测试，而不是继续扩充提示词。

建议保留的最小骨架是：

> 确认用户目标与范围 → 获取现状证据 → 选择最小足够的改造方式 → 定义目标契约和验收 → 实施请求的部分 → 用证据交付；仅在明确请求并具备安全前提时进入迁移与切换。
